# وصال: Social Matchmaking + Micro Digital Gifts

## نطاق الميزة

التفاعلات الاجتماعية الأساسية في وصال مجانية بالكامل: إنشاء منشور نصي أو صورة، الإعجاب، التعليق، المتابعة، والرسائل. لا توجد أي قراءة للمحفظة أو خصم مالي داخل هذه الإجراءات. الهدايا الرقمية اختيارية فقط، وأسعار الكتالوج الحالي بين **1.00 و50.00 ج.م**.

## مخطط البيانات

المخطط موجود في `drizzle/schema.ts` والهجرة المطبقة في:

- `drizzle/0000_chubby_thing.sql`: الجداول الأساسية.
- `drizzle/0001_flippant_master_chief.sql`: إضافة `posts.imageMimeType`.

المبالغ محفوظة في `DECIMAL(12,2)`، ولا تستخدم قاعدة البيانات قيمًا عائمة للأرصدة أو أسعار الهدايا. سجل `gift_transactions` يحتفظ بالمرسل والمستلم والهدية والسياق (`commentId` أو `messageId`) والمبلغ الدقيق ومفتاح منع التكرار.

## إرسال هدية

يوجد المسار الصريح التالي:

```http
POST /api/gifts/send
Content-Type: application/json
Cookie: session=...
```

```json
{
  "recipientId": 42,
  "giftId": 2,
  "commentId": 101,
  "idempotencyKey": "user-42-comment-101-unique"
}
```

يمكن استخدام `messageId` بدل `commentId`، ويجب إرسال واحد منهما فقط. الإجراء المحمي نفسه متاح أيضًا عبر `gifts.send` في tRPC.

مسار الخصم ينفّذ فحص مفتاح التكرار والتحقق من المستلم والملكية ثم ينشئ المحفظة بصفر عند الحاجة، ويستخدم `SELECT ... FOR UPDATE` لقفل صف محفظة المرسل داخل المعاملة. بعد ذلك يقارن المبلغ بوحدات القروش الصحيحة، يخصم السعر عبر تعبير SQL Decimal، ويسجل سجل التدقيق قبل إتمام المعاملة. إعادة إرسال نفس `idempotencyKey` لا تنشئ خصمًا ثانيًا.

## رفع الصور ومنع الفيديو والتحقق من المحتوى

يوفر `feed.uploadImage` إجراءً محميًا يستقبل صورة Base64 بحجم أقصى 5MB، ويفحص magic bytes الفعلية لامتدادات JPEG وPNG وWebP وGIF قبل رفعها إلى S3. بعد نجاح الرفع، يستخدم العميل `url` و`mime` الناتجين عند إنشاء المنشور. لا ينبغي قبول صورة منشور من رابط خارجي في الواجهة الإنتاجية إلا عبر هذا المسار الموثوق.

المخطط يقيد `mediaType` إلى `image` فقط. كما يرفض مسار إنشاء المنشور أي رابط غير HTTPS، وأي امتداد معروف للفيديو، وأي MIME غير موجود ضمن `image/jpeg` أو `image/png` أو `image/webp` أو `image/gif`. يظل فحص مكافحة البرمجيات الخبيثة وحدود معدل الرفع خطوة تشغيلية مستحسنة قبل فتح الرفع العام.

## التكاملات المؤجلة

**تكامل المواصلات أو رصيدها غير منفذ في هذه النسخة**؛ لا توجد هنا مواصفات API أو ملف اعتماد أو نموذج بيانات موثوق من المحادثة الأخرى. عند توفيرها، يجب إضافتها عبر موصل خادمي مستقل، مع صلاحيات محدودة، وتدقيق للطلبات، وعدم نقل أو اختلاق أي رصيد بين المحادثات أو الحسابات. هذا الفصل يمنع خلط بيانات المواصلات بميزانية الهدايا.

## تمويل المحفظة قبل الإنتاج

لا توجد في هذه النسخة عملية شحن رصيد أو بوابة دفع. يجب عدم السماح للعميل بتعديل `wallets.balanceEgp` مباشرة. قبل الإنتاج، يجب إضافة خدمة دفع مصرية أو مزود موثوق، والتحقق من webhooks بتوقيع المزود، وتسجيل كل عملية شحن في سجل ledger منفصل، واستخدام مفاتيح idempotency للشحن أيضًا. يجب أن يتم الشحن من خادم موثوق فقط، مع تسوية دورية ومراجعة يدوية للحالات الفاشلة.

## حالة العناصر المؤجلة

تم تنفيذ أساسيات المنصة المستقلة، بينما تبقى بعض البنود التشغيلية خارج نطاق التنفيذ الفوري: pagination المتقدم للـ Feed، خدمة شحن رصيد حقيقية، واختبار التنافس بقاعدة بيانات اختبارية. هذه البنود لا يجوز تمثيلها أو محاكاتها ببيانات وهمية؛ تُستكمل بعد توفير مزود الدفع وبيئة التكامل والبيانات المطلوبة. تقسيم الحزمة الأساسي مفعّل عبر `manualChunks`، وقد تبقى الحزمة التطبيقية الرئيسية فوق 500KB بسبب مكونات المنتج المتبقية.

## المتطلبات التشغيلية

يستخدم المشروع متغيرات البيئة المدمجة في قالب Full-Stack، وعلى رأسها `DATABASE_URL` و`JWT_SECRET` و`VITE_OAUTH_PORTAL_URL` و`OAUTH_SERVER_URL`. لا يجب حفظ قيم أسرار في المستودع أو في `client`.

لتحديث قاعدة البيانات بعد تعديل المخطط:

```bash
pnpm drizzle-kit generate
# راجع ملف SQL الناتج
# طبّق SQL عبر إدارة المشروع بعد المراجعة
```

ثم يجب تشغيل:

```bash
pnpm run check
pnpm test
pnpm run build
```

## ميزات المنصة المضافة

تحتوي صفحة `/feed` الآن على محرر إنشاء فعلي للنص والصورة. الصورة تمر أولًا عبر `feed.uploadImage`، ثم يُنشأ المنشور بالرابط الداخلي الناتج؛ لا يستطيع العميل رفع فيديو أو تمرير محتوى صورة غير صالح عبر هذا التدفق. صفحة `/profile` تعرض حقول الاسم والعمر والمدينة والنوع والنبذة، ويقبل الخادم تحديث ملف المستخدم الحالي فقط مع تحقق العمر والحدود النصية. كما أضيفت إجراءات `admin.users` و`admin.posts` المحمية بصلاحية `admin` لتغذية لوحة مراجعة لاحقة.

## بيانات الواجهة

صفحة `/feed` تجلب المنشورات والتعليقات والهدايا المرتبطة من قاعدة البيانات، وتجلب الرسائل والهدايا المرتبطة بها للمستخدم المسجل. لا تعرض الصفحة محتوى مستخدمين ثابتًا عند فراغ قاعدة البيانات؛ بل تعرض حالة تحميل أو خطأ أو فراغ مناسبة. بعد نجاح إرسال هدية، يعاد إبطال استعلام Feed أو الرسائل ليظهر الربط البصري تلقائيًا.

## اختبارات الأمان الحالية

الاختبارات في `server/social.rules.test.ts` تغطي رفض الهدية إلى الذات، رفض مفتاح التكرار غير الصالح، وحماية إنشاء المنشور لغير المسجلين. اختبار الطلب المجهول للمسار REST يعيد `401 Unauthorized`. ينبغي إضافة اختبار تكامل بقاعدة بيانات اختبارية للتحقق من التنافس المتوازي والخصم مرة واحدة قبل إطلاق المدفوعات فعليًا.

## التوافق والاقتراحات

تحتوي ملفات الأعضاء على تفضيلات اختيارية للعمر والموقع والاهتمامات وخصوصية إظهار النسبة. يعيد محرك التوافق نسبة تقريبية من 0 إلى 100 مع أسباب مختصرة، ولا تُقدَّم النتيجة كضمان أو حكم نهائي على العلاقة.

## الهدايا داخل غرف الدردشة

يمكن ربط الهدية بتعليق أو رسالة خاصة أو رسالة داخل غرفة. هدايا الغرف لا تُقبل إلا عندما تكون الغرفة في حالة `live` ويكون المرسل عضوًا فيها. الغرف `closed` و`archived` للعرض فقط ولا تسمح بشراء أو إرسال هدايا جديدة. تظل عملية الخصم ذرّية وتستخدم قفل صف المحفظة وIdempotency.

## حدود الجاهزية للنشر

النسخة الحالية جاهزة تقنيًا للمراجعة والنشر التجريبي بعد نجاح الفحوص، لكن الإطلاق التجاري للهدايا يحتاج مزود دفع خارجي وWebhooks موقعة وLedger مستقل قبل تحصيل أموال فعلية. كما أن التخزين دون اتصال الكامل، المكالمات الصوتية/الفيديو، وبعض أدوات إدارة الغرف المتقدمة تحتاج جولات مستقلة.
